# Lab Submission Expectations

Use this checklist with the specific lab tasks posted in Canvas. Starting with **Party Roster and subsequent labs**, these submission requirements and rubric weights stay the same. Publish this document before students begin. It does not add requirements to earlier labs or work already submitted.

## What to submit in Canvas

1. **Git repository link:** link directly to the lab project or its folder. Make sure the instructor can access it using the course-approved permissions. Use a private repository unless public sharing is approved.
2. **Python source files:** upload the completed `.py` file(s), or a ZIP containing them and the small sample files needed to run the lab. Submit the same version that is in Git. Do not include a virtual environment.
3. **Learning journal:** upload a short document or include it in the Canvas ZIP. Describe three key takeaways in your own words, one example of where you applied a skill in the code, and one problem you investigated or fixed. If no problem occurred, describe a check you performed instead. Explain meaningful AI assistance and how you checked it; state if you did not use AI.
4. **Testing and two limitations:** record one ordinary-use test and one relevant invalid-input or failure test, with the input/action and observed result. Describe two things that could break the program or prevent expected behavior. These can include bugs you already fixed: explain what happened and the fix. A limitation is acceptable; you do not need to leave two bugs in the program.

The journal and testing notes may be combined in one document. Keep personal reflections and grade-related material in Canvas rather than making them public.

## Publish the skills in your Git README

Include:

- Project purpose and the lab title.
- Python version, dependencies, and setup/run instructions.
- Required source files and safe sample data.
- A **Skills practiced** section naming what you developed, how it appears in this project, and what you can now explain or do. Do not claim mastery of unfinished features.
- A short usage/output example and known limitations.
- Credit for outside code, data, and meaningful AI help.

Keep the repository professional: understandable filenames, organized files, meaningful progress commits, and no credentials, confidential records, classmates' work, instructor solutions, virtual environments, or textbook PDFs.

Use `requirements.txt` for third-party Python packages. If only the standard library is used, state that and provide the Python version/run command instead.

## How the lab will be graded

## Fixed lab rubric (100 points)

| Criterion | Points | Full-credit evidence |
|---|---:|---|
| Assigned functionality and concepts | 60 | Assigned core tasks work and demonstrate the stated concepts. The Canvas task sheet allocates these 60 points among the required tasks before work begins. |
| Professional Git and source delivery | 20 | Accessible lab Git link and matching Canvas source (8); README purpose/setup/run/dependency information (8); understandable file organization and meaningful progress commits (4). |
| Takeaways and skills | 10 | Journal's three takeaways, code example and problem/check explanation (7); accurate Skills practiced section in Git (3). Include the AI-use/non-use note here; there is no additional AI points category. |
| Testing and limitations | 10 | Ordinary and relevant failure/invalid-input tests with observed results (6); two specific limitations or fixed-bug explanations (4). |
| **Total** | **100** | |

These weights and deliverables remain fixed across future labs. The lab's task sheet identifies the tasks, session scope, due date and allocation of the 60 functionality points. Do not introduce additional deliverables or change these weights through an informal grading note.

- Core tasks are required; stretch goals are optional unless explicitly assigned.
- Equivalent working designs are acceptable when they demonstrate the assigned concepts.
- Partial credit is available for a genuine, explainable attempt.
- A reported or fixed bug can earn reflection credit even when functionality is incomplete.
- Testing may be manual unless automated tests are explicitly required.
- Extra polish, a public repository, paid services, or unassigned features are not prerequisites for full core credit.
- Access problems should be corrected using instructor directions or an approved Canvas archive.
- Do not count one missing item or bug repeatedly across criteria. Functionality assesses behavior; journal/testing assesses the student's explanation and evidence.

## Before submitting

Run the uploaded version, check that the README directions work, verify the Git link's access, and confirm that your code, journal, skills statement, and tests agree.

**Assignment-specific details:** use the lab's Canvas post for its title, required tasks, rubric, due date, repository permissions, and any approved accommodation. If instructions conflict, ask the instructor before the deadline.
